# ADR-0001: Alembic owns the database schema

- **Status**: Accepted
- **Date**: 2026-09-16

## Context

The app called `SQLModel.metadata.create_all()` on every startup, while CI separately ran
`alembic upgrade head` on merges to `main`. Two mechanisms managed one schema. This hid a
defect: the "initial schema" migration had been autogenerated against a database
`create_all()` had already built, so no migration had ever created a table, and
`alembic upgrade head` failed on an empty database.

## Decision

Alembic is the only mechanism that changes the schema. Application startup performs no schema
work and no writes; it verifies the database is reachable and continues either way.

## Consequences

- A fresh environment needs `alembic upgrade head` before the app is useful.
- Migrations are the reviewable record of every schema change, including the pgvector tables
  planned for Phase 1.
- Autogeneration must run against a database *built by migrations*, never against one built by
  `create_all()`. `tests/test_migrations.py` enforces that a fresh upgrade reproduces the
  models.
- Migrations must be backward-compatible with the previous deployment, because rolling back a
  deployment does not roll back the schema.
- The baseline revision was rewritten in place, keeping its id, so that an already-migrated
  production database needed no manual step. This changes `downgrade` for that revision and is
  recorded in the revision's docstring.

## Alternatives considered

- **Keep `create_all()` as a fallback.** Rejected: it is exactly what masked the broken
  migration history.
- **Squash to a new baseline revision id.** Rejected: it would have required a manual
  `alembic stamp` against production before the change could merge.
