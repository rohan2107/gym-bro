# Audit: September 2026

**Date**: September 16–20, 2026
**Trigger**: resuming development after a seven-month pause (last substantive change: February
2026). The documentation described a state that no longer matched the code.
**Method**: every claim in the docs was checked against the code, the tests were run, the
project was built from a clean checkout, and the deployed site was probed.
**Outcome**: 14 findings fixed in [PR #16](https://github.com/rohan2107/gym-bro/pull/16);
6 remain open and are listed at the end (O5 and O6 were fixed afterwards in M0.2).

The summary is that the engineering underneath was good (atomic rate limiting, streamed
uploads with size caps, per-user isolation at the dependency layer, injectable services), but
several of the things built on it were not what the documentation said, and two defects would
only ever have appeared in production.

## Details

### F1: Vision was a stub

`VisionService.client` was hardcoded to `None`, the real implementation was commented out, and
mock mode returned a fixed `{"label": "pizza", "confidence": 0.85}`. The README documented
photo analysis via Google Vision and USDA as working, and there was no UI to reach it.

**Resolution**: implemented against the Vision REST API (`images:annotate`) with `httpx`.
Web-entity scores are unbounded relevance values rather than probabilities, so they are
thresholded on the raw value and clamped; generic labels ("Food", "Tableware") are filtered
before nutrition lookup. See [ADR-0002](adr/0002-vision-rest-api-with-header-credentials.md).

**Verification**: unit-tested against a mocked endpoint. **Not verified live**, because Vision
requires a billing account; see [ADR-0003](adr/0003-hard-capped-providers-only.md) and
[M0.3a](ROADMAP.md#m03a-food-recognition-providers).

### F2: `pillow` missing from production

Vercel installs `api/requirements.txt`, which did not list `pillow`, while the photo endpoint
imported it. CI installed a different file that did. Green CI, broken production.

**Resolution**: both files aligned; `tests/test_requirements_parity.py` fails the build on any
future drift.

### F3: Requirements drift

Beyond `pillow`, the files pinned different `alembic` versions, and one was UTF-16LE with CRLF
line endings (a PowerShell artefact). Both are now UTF-8 with identical shared pins.

### F4: Placeholder user in production

`init_db()` inserted user `id=1`, `temp@gymbro.app`, commented "temporary until OAuth is
implemented". OAuth shipped in February 2026, but the seed ran on every serverless cold start
against the production database.

**Resolution**: removed. `check_db_connection()` reads only, and tests assert startup neither
creates tables nor writes rows.

### F5: Two schema owners

`create_all()` at startup competed with `alembic upgrade head` in CI. Alembic could not be the
source of truth while another mechanism silently built the same tables.

**Resolution**: `create_all()` removed from the startup path.
See [ADR-0001](adr/0001-alembic-owns-the-schema.md).

### F6: Overbroad CORS

`allow_origin_regex=r"https://.*\.vercel\.app"` with `allow_credentials=True` made every site
on `vercel.app` an allowed credentialed origin. The `SameSite=Lax` cookie limited the practical
impact, but the documentation claimed the production domain was pinned.

**Resolution**: an explicit allow-list. A regex that looks project-scoped
(`gym-bro-[a-z0-9-]+`) is not: anyone can deploy a project with that prefix. The optional regex
setting defaults to empty, because on Vercel the frontend and API share an origin and CORS is
never consulted.

### F7: Configuration outside `Settings`

`GOOGLE_VISION_API_KEY` and `USDA_API_KEY` were read with `os.getenv`, so the environment
contract lived in several places and was enforced in none. All keys are now declared on
`Settings`, and an autouse test fixture forces mock mode so a developer with real keys in
`.env` cannot make the suite issue billable calls.

### F8: Stale documentation

Job counts, test counts, feature status and the CORS claim were all out of date. Replaced by
the documentation restructure recorded in the [changelog](../CHANGELOG.md).

### F9: Windows-only tooling

All six developer scripts were PowerShell, unusable on macOS or Linux. Shell equivalents were
added; the `.ps1` files remain for Windows.

### F10: Lint version drift

CI installed ruff unpinned, with no configuration in the repository, so the rule set was
whatever the latest release defaulted to. On ruff 0.16.7 an untouched `main` produced 202
findings. `gymbro-api/ruff.toml` now states the rule set and the version is pinned.

### F11: No migration created a table

The "initial schema" revision was autogenerated against a database that `create_all()` had
already built, so it contained only an index change. The whole schema existed because
`create_all()` ran on every cold start. Removing that (F5) exposed it: `alembic upgrade head`
on an empty database failed with `no such index: ix_user_email`.

**Resolution**: the baseline was rewritten to create every table. The revision id is unchanged
and the photo columns stay in the second revision, so an already-migrated database sees no new
work on `upgrade`. Rewriting an applied revision breaks the usual rule and changes
`downgrade`, which now drops the schema; the revision docstring records this and why the
alternative (a new revision id needing a manual `alembic stamp` first) was judged worse.

**Verification**: `tests/test_migrations.py` builds a database from migrations alone and
asserts tables, columns and indexes match the models. Production was confirmed at head
(`573ff5ce6812`) before merge, so the `db-migrate` job was a no-op.

### F12: Impersonation header open in production

`get_user_id()` honoured an `X-User-Id` header whenever `ENVIRONMENT` was `development` or
`test`, and defaulted to `development` when unset. `ENVIRONMENT` was never set on Vercel, so
production accepted the header from anyone: a caller could read or write any user's data by
naming their id.

**Confirmation**: on September 20, 2026, `X-User-Id: 999999999` returned `200` on the live site
and the same request without the header returned `401`. The probe used an id that cannot
exist, so no real data was touched. The flaw predates this audit.

**Resolution**: the header is enabled only when `ENVIRONMENT` is explicitly `development` or
`test`; the `Settings` default is `production`; and it is never enabled when `VERCEL` is set,
which Vercel sets itself, so a misconfiguration cannot reopen it.

**Verification**: tests cover the unset case, an explicit `development` on Vercel, the
settings default, and an end-to-end request. The live site returned `401` after the fix was
deployed.

Mock mode was closed in the same change: it returns fixed sample data, which on a deployment
would present fabricated nutrition as a real analysis, so the endpoint now returns `503`
before spending quota.

### F13: API key in the request URL

The first Vision implementation sent the key as `?key=`. `httpx` includes the full request URL
in `HTTPStatusError`'s message, and the photo endpoint logs that exception with
`exc_info=True`, so any Vision HTTP error would have written the key into application logs.
Reproduced before fixing. The key now travels in an `X-Goog-Api-Key` header, which Google
documents as the recommended form, with regression tests asserting it appears in neither the
URL nor the raised exception.

### F14: Internal error text shown to users

Uploading a HEIC file from macOS returned `Invalid image file: cannot identify image file
<_io.BytesIO object at 0x…>`. HEIC is now recognised by its file signature and rejected with a
message explaining how to get a JPEG, and the generic path returns fixed text. See
[PHOTO_ANALYSIS.md](PHOTO_ANALYSIS.md).

## Open findings

Found during the audit and not yet fixed. Scheduled work is linked; the rest are in the
[roadmap backlog](ROADMAP.md#backlog).

| ID | Finding | Notes |
|---|---|---|

| O3 | Raw provider error text is returned to the client on a failed token exchange | Leaks upstream detail; should be logged and replaced with a fixed message |
| O4 | The callback page's effect runs twice in development, so the second request reuses a single-use code and returns `400` | Benign, and does not occur in a production build |
